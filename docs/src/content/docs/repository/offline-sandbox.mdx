The claim this repository makes is that a machine with no network can reconstruct a
working environment from a git branch.
[pixi-sandbox](https://github.com/Archont561/pixi-sandbox) owns that surface, and
this repository uses its tasks rather than growing a second implementation.

## The reviewed plan

`.pixi-sandbox.toml` is the publish plan, and it is short enough to read in full:

```toml
schema        = 1
branch_prefix = "sandbox"
cargo_vendor  = false

[[bundle]]
name         = "developer"
environments = ["default", "bun"]
platforms    = ["linux-64"]
```

Two of those lines are decisions rather than defaults:

- `cargo_vendor = false` because there is no Cargo workspace here. A `true` would add
  an empty vendor tree to every transport and a `.cargo/config.toml` pointing at it on
  every restored machine. If a Rust crate is ever added, this becomes `true` in the
  same commit that adds the crate.
- `environments = ["default", "bun"]` — **both**. A transport that packed only
  `default` would restore a machine that cannot run turbo, which is the same as no
  restore at all.

## Packing and publishing

<Steps>

1. **Validate the plan.** Cheap, needs neither environment, and runs as its own CI
   job so a malformed contract reports in under a minute instead of waiting behind a
   QGIS solve.

   ```bash
   pixi run sandbox-plan
   ```

2. **Pack, then verify.**

   ```bash
   pixi run sandbox-pack
   pixi run sandbox-doctor   # doctor --verify: every declared byte, writes nothing
   ```

3. **Publish.** `.github/workflows/publish-sandbox.yml` does the real publish on a
   push that touched an input of the snapshot; `pixi run sandbox-publish` is the
   local equivalent. The transport lands on an orphan branch —
   `sandbox/developer-linux-64` — so it shares no history with `main`.

</Steps>

## Restoring

On the airlocked machine, with the repository already transferred:

```bash
pixi run sandbox-restore     # or: bash scripts/restore.sh
source .pixi/sandbox-env.sh
pixi install --frozen --offline --all
```

`scripts/restore.sh` never guesses the branch name: it reads the same reviewed plan
the publisher uses, so a renamed prefix or a new bundle reaches the restore path for
free. It prefers objects that are already local — a disconnected host is the whole
point — and only fetches when the branch is genuinely missing. Afterwards it sources
the generated `.pixi/sandbox-env.sh`, which puts the bundled tools *and* every
restored environment's `bin/` on `PATH` by itself; no environment name is hardcoded
in the script, so a bundle whose environment is not called `default` still works.

<Aside type="caution" title="What verification does not prove">
  `doctor --verify` compares every declared byte against the manifest, and
  `--verify-restored` re-checks the tree that came out the other end. Neither is an
  egress test. `pixi install --offline` is a *request*, not an enforcement: over a
  live network a damaged prefix is quietly re-fetched and the command reports
  success. If that proof is wanted, it belongs as a `pixi run` task a human triggers
  under `unshare -n`, not as a workflow that silently skips its authoritative tier.
</Aside>

<Aside type="note" title="Generated files with local edits">
  `.pixi-sandbox.toml`, `.github/workflows/publish-sandbox.yml`, `scripts/restore.sh`
  and `scripts/restore.ps1` are generated by `pixi-sandbox init github`. Regenerating
  means deleting all four, re-running the installer, and **reapplying the edits marked
  `LOCAL EDIT` in each file's header**. Those edits are policy, not drift.
</Aside>
